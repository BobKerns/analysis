# ADR-006: Ensemble scenarios — parameter variation and Monte Carlo runs

- **Status:** Accepted
- **Date:** 2026-09-29
- **Supersedes:** —
- **Amended:** see [Amendments](#amendments) at the end.
- **Related:** [ADR-001](ADR-001-overall-architecture.md) (overall architecture), [ADR-002](ADR-002-storage-schema.md) (storage schema, `scenario.seed` — "reserved for ensembles; unused in v1"), [ADR-003](ADR-003-registries-and-csv-schemas.md) (registries, CSV layouts, calendar events §3, scenario hierarchy §4.5), [ADR-004](ADR-004-reproducibility-and-activation.md) (reproducibility, provenance).

## Context

Every scenario today is one deterministic prediction. We want to ask "what if this rate, or this date, or this one-off amount, is actually somewhere in a range" and see the *spread* of outcomes: generate many variants of one scenario, each with specific parameters redrawn from a distribution, run all of them, and combine the results (mean, median, standard deviation, range) rather than reading one number.

Two design questions turned out to matter more than the rest:

**Where does the perturbation happen?** Not against a run file. A run file's entire reason for existing is "the fixed, immutable result of simulating a fixed intent" — mutating one mid-lifecycle (even before simulation starts) makes "patch already-simulated ledger data" a reachable mistake later, not just a theoretical one, since a change to an early month's input would need every later month recomputed to stay consistent, which is exactly what running already does. **Perturbation happens once, at the intent stage, before any run exists.** `run_scenario`/`open_run_file` need no ensemble-awareness at all: an ensemble member is an ordinary intent file, run by the ordinary, completely unmodified `run_scenario`.

**What authors "this value should be drawn, not fixed"?** Not a new file. `calendar.csv` already has `set_rate`, `set_amount` and `one_off_transfer` events that patch exactly the columns we want to vary, at exactly the granularity we want (one row, one target). Extending `calendar.csv` with optional "instead of a literal, draw one" columns means variation authoring gets calendar reporting for free, and "vary" reduces to resolving those columns and writing ordinary calendar rows with concrete numbers — no new engine mechanism, no separate spec file to keep in sync with what it targets.

## Decision

### 1. Pipeline: load → vary → run

```text
recipe scenario's CSVs  --sim load-->  recipe intent (calendar rows with unresolved
                                        vary_* columns; not meant to be run as-is)
                              |
                              | sim run <recipe>  (auto-detects unresolved rows)
                              v
        for each member: copy the recipe intent, resolve every vary_* row by
        drawing a value and writing it back as an ordinary calendar_event row
                              |
                              v
              member intent (state/intent/<recipe>/member_0001.sqlite3, ...)
                              |
                              | run_scenario(member_intent, member_run)  -- UNCHANGED
                              v
                member run   (state/runs/<recipe>/member_0001.sqlite3, ...)
```

`sim load` is completely unchanged: a recipe's CSVs load into one intent exactly like any scenario's. `run_scenario`/`open_run_file` are completely unchanged: they've never heard of ensembles and don't need to. All new logic is the **vary** step in between, and it only ever writes ordinary, already-supported calendar rows.

### 2. `calendar.csv` gains `name` and optional `vary_*` columns

`calendar.csv` rows have no author-facing stable identity today (which also blocks calendar-event tagging — nothing keys on a specific row). Both gaps close with the same, small, backward-compatible addition:

| column | required | notes |
| --- | --- | --- |
| `name` | for a row with `vary_distribution` set; optional otherwise | stable identifier, unique within the scenario |
| `vary_target` | with `vary_distribution` | `amount` or `date` — which of *this row's own* columns is drawn instead of literal. Exactly one target per row — a `one_off_transfer` whose amount and date are both uncertain is two authoring passes (§5), not one row with two draws. |
| `vary_distribution` | to mark this row as varying | `uniform`, `truncated_normal`, `triangular` or `discrete`; blank means an ordinary literal row, unaffected by any of this |
| `vary_low`, `vary_high` | see notes | `uniform`'s own bounds (both required), in the target column's own unit: the row's own `amount` unit for `vary_target='amount'` (a percent with its `%` sign for `set_rate`, dollars for `set_amount`/`one_off_transfer`, as that row's own `amount` cell is written; the loader converts them to micros or cents like the `amount`), a date for `vary_target='date'` (a full `YYYY-MM-DD` is kept exactly; a bare `YYYY-MM` is the month's first day as `vary_low`, its last as `vary_high`, and its 15th as `vary_mode`, stored as that ISO date, #34). Also `triangular`'s bounds (both required), and `truncated_normal`'s own optional clip bounds (`vary_target='amount'` only) — see `vary_median`/`vary_sd` for how either may be left blank |
| `vary_median`, `vary_sd` | for `truncated_normal` | same unit rule as `vary_low`/`vary_high`; `vary_target='amount'` only — `truncated_normal` is rejected with `vary_target='date'` (`vary_sd` is a numeric spread, not a date span). `vary_median` is the median of the *truncated* distribution, so the base case (§9) is exactly the authored value even with asymmetric bounds; it must lie strictly between the bounds. `vary_sd` is the scale of the underlying distribution before clipping: its standard deviation for the default shape, but only a scale factor once `vary_skew`/`vary_tailweight` are set (the implied SD is reported by `distributions.moments`). Any one of `vary_median`/`vary_sd`/`vary_low`/`vary_high` may be inferred from the others when left blank: `vary_median` defaults to the midpoint of `vary_low`/`vary_high` (both required in that case); `vary_sd` to the distance from `vary_median` to whichever of `vary_low`/`vary_high` is given, divided by 3 (both must imply the same `vary_sd` if both are given with an explicit `vary_median`), for the default shape only — with `vary_skew`/`vary_tailweight` set, `vary_sd` must be given; a still-blank `vary_low`/`vary_high` to the untruncated distribution's ∓3 standard-normal-score points (`vary_median ∓ 3 × vary_sd` for the default shape). `truncated_normal` is therefore never actually unbounded — see §3. **`vary_mean` (before #31) is rejected with a "renamed to `vary_median`" error**, not aliased: its meaning changed for asymmetric bounds |
| `vary_skew`, `vary_tailweight` | optional, `truncated_normal` only | unitless sinh-arcsinh shape (§3): skew 0 (default) is symmetric, positive a longer high tail; tail weight 1 (default) is normal, below 1 heavier tails, above 1 lighter |
| `vary_mode` | optional, `triangular` only | the peak (most likely value), in the target's unit; defaults to the midpoint of `vary_low`/`vary_high` |
| `vary_outcomes` | for `discrete` | `;`-separated outcomes, each `weight: value` or `weight: low..high` (`30%: 0; 25%: 1000..6000; 45%: 6000..20000`); weights are percents with their `%`, adding up to 100%; values in the target's unit as for `vary_low`/`vary_high`, a bare `YYYY-MM` being the 15th as a value and the month's first or last day as a range end. See §3 |
| `vary_ramp_months` | optional, `vary_target=amount` on a `kind=set_rate` row only | see §4 |
| `vary_process` | optional, `vary_target=amount` on a `kind=set_rate` row only | blank (one held draw, as before) or `ar1`; see §4a. Not combined with `vary_ramp_months` |
| `vary_persistence` | with `vary_process` | the process's φ, `0 <= φ < 1`: how much of one year's departure from the level carries into the next. 0 makes every year independent |
| `vary_shock_sd` | with `vary_process` | the size of one year's shock, a percent like the row's own rate (`17%`), `> 0`; see §4a for how it applies. Formerly `vary_innovation_sd`, now rejected with a rename error (#284) |
| `vary_process_start` | optional, with `vary_process` | where the path starts: blank for a stationary start around the level, or `current` for the rate in effect just before the row's date, reverting to the level at `vary_persistence`; see §4a |
| `vary_resume` | optional, on a `kind=set_rate` row with no `amount` and no other `vary_*` value | a date before the row's own, usually an episode's start marker: the row puts back whatever governed its series the day before it; see §4b |

`vary_target='amount'` is only valid on a kind whose `amount` column means something to vary (`set_rate`, `set_amount`, `one_off_transfer`); `retire_scheduled` and `transfer_balance` have no amount to vary, so only `vary_target='date'` is valid there. A distribution's own parameter columns are the only ones it may set — `vary_median`/`vary_sd` alongside `uniform` is rejected as a parameter the draw would silently ignore. Bounds must be orderable where that means something: `vary_low <= vary_high` (strictly below for `triangular` and `truncated_normal`), `vary_sd > 0`, `vary_tailweight > 0`, `vary_low <= vary_mode <= vary_high`.

A process (§4a) is checked at load like the rest. `vary_process` is accepted only on a varying `kind=set_rate` row with `vary_target='amount'`, and any value but blank or `ar1` is rejected. With `vary_process` set, `vary_persistence` and `vary_shock_sd` are both required; either one, or `vary_process_start`, without it is rejected as a parameter nothing would read. `vary_process_start` is blank or `current`. A `current` start needs a rate to start from: an entry of the row's series file dated before the row, or an earlier `set_rate` row for the same `(aux_kind, series)` with a fixed date; with neither, the load fails. A row whose date varies doesn't count, since it could land after the process row. `vary_persistence` must be finite with `0 <= φ < 1`, `vary_shock_sd` finite and `> 0`, and `vary_ramp_months` must be blank. The level's effective lower bound, explicit or inferred (§2's ∓3 default), must be above −100%, since `1 + L` must be positive for the path's growth factors to mean anything.

A resume row (§4b) is checked at load too. `vary_resume` is accepted only on a `kind=set_rate` row with no `amount` and no other `vary_*` value, since it puts back a rate rather than setting one. Its date, after a relative date is placed at the markers' base case, must come before the row's own, and the series must have a rate in effect before it, as for a `current` start.

A row's dates may be written relative to a `date_marker` row ([ADR-003](ADR-003-registries-and-csv-schemas.md) §3.8, [#281](https://github.com/BobKerns/analysis/issues/281)): `NAME+2y` in `date`, or in a date row's `vary_low`/`vary_high`/`vary_mode`. The marker is the one thing that varies, so a row whose amount varies, a process row included, can still move with an uncertain event, without a second set of distribution columns.

A row's own `date`/`amount` column still holds a placeholder when it's the vary target (schema requires a value; nothing reads it). `_apply_calendar_event` gains one defensive check: firing a row that still has `vary_distribution` set is always a mistake — a recipe run directly, or a resolution step skipped — so it raises rather than silently using the placeholder. This check also runs once, up front, over every `calendar_event` row before the monthly loop starts, so a row dated outside the scenario's range or of a kind the engine doesn't otherwise apply can't skip the check by never being visited. This is the only engine change in this ADR.

### 3. Distributions

The registry is closed, but adding a family is additive, not a redesign. Every family exposes `quantile(q)`, which sensitivity analysis (ADR-007) and correlated draws (#30) build on.

- **`uniform(low, high)`** — equal probability across the range. Suits a date range or an amount when nothing in the range is more likely than the rest.
- **`truncated_normal(median, sd, clip_low, clip_high, skew=0, tailweight=1)`** — a normal, or with `skew`/`tailweight` a **sinh-arcsinh normal** (Jones & Pewsey 2009, #31), restricted to the clip bounds. The underlying variable is `location + sd · sinh((asinh(Z) + skew) / tailweight)` with `Z ~ N(0, 1)`, which is exactly the normal at the defaults. `location` is solved numerically so the **truncated** distribution's median is exactly `median`. For the normal and lighter tails any median strictly inside the bounds is reachable in principle; in practice one hugging a bound relative to `vary_sd` (where the fit would need the distribution centered dozens of standard scores away, beyond double precision) is a load error asking for a smaller `vary_sd`. With heavy tails a median pushed toward a bound against the skew may genuinely be unreachable, which is a load error naming the reachable range. Shape values too extreme to compute (overflow) or non-finite are load errors too. Its CDF and quantile are closed-form with `statistics.NormalDist` (no scipy), so draws are **inverse-CDF** (`quantile(u)` for uniform `u`): exact for any shape, never a rejection loop. (Before #31 this was a rejection sampler around a *mean*; existing seeds now draw different, equally valid values.) `truncated_normal`'s name commits it to always being bounded: an unbounded `normal` is deliberately not offered, since an unclipped draw is a footgun (an outlier arbitrarily far out passing straight to the engine). The clip bounds therefore default to the ∓3 standard-normal-score points (§2). A median can't sit on a bound (half the mass would have to be on it): the old "set `clip_low` to the mean for a one-sided draw" is now expressed with `skew`.
- **`discrete(outcomes)`** (#165) — a few separate outcomes with weights, each a single value or a `low..high` range spread evenly: "30% nothing, 25% a little, 45% somewhere from a little to a lot". It is the family for a bet whose outcomes are distinct cases rather than one continuum, since only it can put real probability on one exact value (a zero). Outcomes are kept in value order, so its quantile is monotone, a step at a single value and linear across a range, and sensitivity (ADR-007) and correlated draws (ADR-008) treat it like any family. Valid for a date target as well as an amount; a date range gives each of its whole days equal weight, as `uniform` does. A range's low end must be below its high end (a single value is written without `..`). Outcomes may share a range end but not otherwise overlap; the weights must add up to 100%. Its moments are computed outcome by outcome, so even a tiny single-value outcome counts. A `one_off_transfer` outcome may be exactly 0 (a transfer of nothing), the one exception to the positive-amount rule for transfers; a negative one is still rejected.
- **`triangular(low, mode, high)`** (#31) — rising linearly to a peak at `mode`, then falling: the **three-point estimate** ("most likely X, no earlier/lower than A, possibly as late/high as B"). Valid for a date target, where it is the only skewed choice — e.g. a home sale that most likely closes in June, can't close before April, but could slip to December. Its quantile is closed-form.

**Dates are drawn in whole days, though the simulation steps monthly.** An event fires in the month containing its date, so a date draw mostly selects a month. Drawing days rather than months is still the right unit, for two reasons. First, it weights each month by its length: a range uniform "over this span of time" makes a 31-day month about 3% likelier than a 30-day one, and February less likely, where drawing months would treat them all alike. Second, the day still matters within its month wherever a rule compares dates: a rule stops in any month whose month-end is past its `end`, so a `retire_scheduled` date anywhere before the 31st of a 31-day month already stops that month's payment, while the last day doesn't. A date's moments (`distributions.moments(..., whole_days=True)`) are computed over whole days to match.

Each family's center (§9) is its median: `uniform`'s midpoint, `truncated_normal`'s authored median, `triangular`'s median (between its mode and its longer side), `discrete`'s median (which, for a bet with a large chance of nothing, is often the nothing). `distributions.moments` reports any family's implied mean, SD, skewness and excess kurtosis, so authors can see what shape parameters mean in practice (ADR-007's parameters table shows them).

Every draw uses an **independent RNG stream per (member, row name)** (a row in an [ADR-008](ADR-008-correlated-parameters.md) correlation tree uses its stream for its own noise, combined with its parent's score), derived by hashing `(ensemble seed, member index, row name)` through `hashlib.sha256` into a `random.Random` seed. One shared stream in call order would mean adding or removing one variation silently shifts every other variation's draws for every member; keyed streams don't.

A `vary_process` row draws its level in the amount pass like any other amount row, then expands its path (§4a); the path's yearly shocks are drawn on streams of their own, so adding a process to a row shifts no other row's draws, and none of that row's own level draw.

**Two passes, in this order: every `vary_target=date` row first, then every `vary_target=amount`/rate row.** A ramp's reference point, or an amount meant to reflect "whatever the ramped rate is as of this (possibly also-varying) date," needs the date side already resolved before the amount side draws — resolving dates first makes that always true rather than order-dependent by accident.

### 3a. A varying lifespan

A person's lifespan varies too ([#221](https://github.com/BobKerns/analysis/issues/221)): `lifespan.csv`'s `age_at_death` can carry `vary_distribution` (`uniform` or `triangular`, with `vary_low`/`vary_high`/`vary_mode` in years; or `life_table`, below) ([ADR-003](ADR-003-registries-and-csv-schemas.md) §4.9). Each member draws an age, rounds it to whole months, and writes it and the final month it reaches into `person_lifespan`, clearing `vary_distribution`. The engine reads only the final month, so the `on_death` sweep, RMDs, Social Security and every lifespan-gated rule, and the filing-status switch all follow the draw.

**From a life table** ([#222](https://github.com/BobKerns/analysis/issues/222)): `vary_distribution=life_table` draws the age from the person's life table for their sex: the aux `life_table.csv`, or the `life_table__<name>.csv` that their `lifespan.csv` row's `life_table` names ([#315](https://github.com/BobKerns/analysis/issues/315)). The table is conditioned on the person being alive at the scenario start and read with the age set-forward that the loader solved, so that its median is `age_at_death` ([ADR-003](ADR-003-registries-and-csv-schemas.md) §4.9). A member maps its probability (a fresh draw, a correlated score's, or an OAT quantile) through the inverse of that distribution, in whole months. So the author states one number they believe, the median, and the table supplies the skewed shape of real mortality around it: a long early tail and a short late one.

The adjustment is a set-forward alone, with no mortality multiplier. Adult mortality from about 40 to 95 follows the Gompertz law: the death rate grows by a nearly fixed factor each year, doubling about every eight years. Under that law, multiplying every year's rate by `m` is exactly reading the table `ln(m)/b` years older. So once the set-forward is solved to keep the median, a multiplier has almost nothing left to change. On SSA's 2023 table, for a man 70 at the start with a median of 80, multipliers from 100% to 500% move the 90th-percentile age only from 88.4 to 90.6. A different median is a scenario comparison, and the uncertainty around it is the draw itself or a sensitivity sweep. A varying multiplier, or a median that itself varies, would add complexity with no basis beyond the same judgment that sets the median.

A lifespan behaves like any varying row: its stream is keyed by `lifespan:<person>`, its node name in correlation trees ([ADR-008](ADR-008-correlated-parameters.md)) and sensitivity sweeps ([ADR-007](ADR-007-sensitivity-analysis.md)), and `ensemble_draw` records the age with target `age_at_death`. One difference: its base case (§9), member 0 and any OAT member that doesn't move it, is the authored `age_at_death`, not the distribution's median, so a run dies at the age written down. (For `life_table` the two coincide.) A triangular's mode defaults to that age, so the base case is the most likely value.

### 4. Ramps: one authored row, several generated rows

A `kind=set_rate` row with `vary_ramp_months` set draws its **target** the same way any `amount` variation does, then **expands**: instead of writing one resolved `set_rate` event, the vary step writes `vary_ramp_months` of them, one per month, linearly interpolated from the series' current value (its latest series-file entry or `set_rate` row on or before this event's own `date`, an earlier varying row counting with its resolved value, §5) up to the drawn target, landing on it at `date + vary_ramp_months`. One authored row with several synthesized effects is not a new category of calendar event, nor a new way of reading `aux_table`: every generated row is an ordinary dated `set_rate`, looked up exactly like any other rate series (latest row on or before the month). The smoothing is entirely in what the generator writes, not in how anything reads.

This also resolves "future stock prices": the engine never simulates a price path day to day (`security_price` is consulted once, to derive an opening balance — [ADR-005](ADR-005-lots-and-per-lot-state.md) §6). Varying a lot's future price expectation is varying its growth-rate assumption, so `set_rate` (jump, ramp or process, §4a) covers it; no separate stock-price mechanism is needed. Modeling a sudden jump is rarely the realistic prediction, which is the whole reason the ramp exists.

### 4a. Processes: a year-by-year path from one row

A held rate (one draw per member, kept until the next row for that series) suits a persistent quantity such as an inflation rate or a yield, whose level carries over from year to year. It doesn't suit a rate of return: annual stock and bond returns have essentially no year-to-year persistence and a large spread, and holding one constant removes the year-to-year volatility that sequence-of-returns risk depends on. A `set_rate` row with `vary_process = ar1` keeps its draw as the path's **level** and expands into one `set_rate` row per year that moves around it.

With `L` the row's drawn level (its value, exactly as a held row would draw it, correlated through any [ADR-008](ADR-008-correlated-parameters.md) tree as before), `φ` its `vary_persistence`, `σ` its `vary_shock_sd` and `εₖ` the shock for year `k` (a standard normal, or in a t-copula tree a scaled one, below). `L` and `σ` are authored as percents and enter the equations as decimals, so 7% is `L = 0.07`:

```text
x₀    = ε₀ · σ / sqrt(1 − φ²)          stationary start: year 0 is already uncertain
xₖ    = φ · xₖ₋₁ + σ · εₖ              k = 1, 2, ...
xₖ    = clamp(xₖ, −5, 5)               numerical guard only, see below
rate_k = 12 · ((1 + L/12) · exp(xₖ/12) − 1)   as the engine's annual rate, rounded to micros
```

- **Starting at the current rate** (#280). With `vary_process_start = current`, the path starts at `r_current`, the rate in effect for the row's `(aux_kind, series)` on the day before its date, and reverts from there instead of starting with a draw:

  ```text
  x₀    = 12 · ln((1 + r_current/12) / (1 + L/12))   no shock: year 0 is the current rate
  xₖ    = φ · xₖ₋₁ + σ · εₖ                          k = 1, 2, ... as above
  ```

  The departure decays as `φᵏ`, with each year's shock on top, so the series' own persistence sets how quickly it returns: with `φ` near 0 a year, with `φ` at 0.7 several. Its excess over the level adds as much to the price level as a step lasting `1/(1 − φ)` years. `r_current` is whatever the scenario says at that date: the series file's latest entry before the row, or an earlier `set_rate` row's value, using its resolved value if it varies (a held draw, or a ramp's or a path's last step). A series-file entry on the row's own date doesn't count, because the row replaces it. Updating "now" therefore means updating the series file, not the calendar. Year 0 is `r_current` exactly; the tree still draws its year-0 noise for the other rows in it, but the path uses none, and `ensemble_path_shock` records its year-0 shock as 0. `L` is drawn as before and is what `ensemble_draw` records.
- **The path works in growth factors, not rates.** The engine applies a `set_rate` value `r` as `r/12` a month, so a year at `r` grows by `(1 + r/12)¹²`. The path sets that year's factor to `(1 + L/12)¹² · exp(xₖ)`, a held row's factor times `exp(xₖ)`, which is the `rate_k` above. A growth factor therefore never reaches zero, and the path's **compound** growth has median `(1 + L/12)¹²` a year, exactly a held row's, because the shocks' sum has median 0. Adding the shock to the rate instead would make the path compound to less than `L` by about half the shocks' variance, so a stock path authored at 7% with a 17-point annual SD would compound to under 6%. `L` therefore means "the rate this path compounds to, in the median future", the same thing a held row's value means.
- **`σ` is in growth-factor terms.** `σ` is the SD of the yearly shock to the log of a year's growth factor, written as a percent as if it were a rate. A historical annual rate is a year's whole growth, so it is the SD of `log(1 + rate)` net of persistence, which `analysis historical` reports as Shock SD. At the sizes in question (a few points to about 20) it is within a point or two of the plain annual SD.
- **What `εₖ` is depends on the tree.** For a row in no tree, or in a Gaussian tree, `εₖ` is a standard normal and `σ` is exactly the yearly shock SD. In a t-copula tree with `ν` degrees of freedom, `εₖ = Sₖ · zₖ`, where `zₖ` is the row's Gaussian year-`k` score and `Sₖ` the tree's year-`k` scale ([ADR-008](ADR-008-correlated-parameters.md) §5), so `εₖ` is Student-t with `ν` degrees of freedom and the yearly shock SD is `σ · sqrt(ν / (ν − 2))`. A tree holding a process row therefore requires `ν > 2` (a load error otherwise), so that SD is finite. `σ` means the same thing in both cases, the shock's scale, and a t-tree's heavier tails come with a larger SD; the calibration guide says to divide a measured yearly SD by `sqrt(ν / (ν − 2))` when the row sits in a t-tree. The start `x₀` uses `ε₀ = S₀ · z₀` the same way, which is an approximation: the stationary law of an AR(1) with t shocks is not itself a scaled t, but its SD matches.
- **A numerical guard, not a bound.** Clamping `xₖ` to ±5 keeps `exp(xₖ)` finite whatever the inputs (a factor between 0.007 and 148). Realistic inputs never reach it: with `σ` at 20 points and `φ` at 0.9 the stationary SD of `xₖ` is under 0.5, so ±5 is past ten standard deviations, though a heavy-tailed t-tree reaches it sooner. It exists so a mistyped `σ` produces a bad scenario rather than an overflow.
- **Steps.** Generated row `k` is dated `k` years after the authored row's date (month-end, the same month), year 0 being the authored row itself, which takes `rate₀`. Generation stops after the scenario's last month, and before the date of the next authored `set_rate` row for the same `(aux_kind, series)`, which takes over from there (next in the engine's order, date then row, so a later row on the process row's own date takes over at once); that row may be a process too, and "next" uses its resolved date after pass 1. Each generated row carries the authored row's series and payload (its `aux_kind` and the rest of `params_json`), as a ramp's do, so it is the same rate change with a different date and value. A rate holds for 12 months between steps, so the path is a sequence of annual rates, which is the scale at which persistence is calibrated; a monthly path would add rows without changing outcomes much.
- **No bounds on the path.** The row's bounds (`vary_low`/`vary_high`, explicit or the ∓3 SD defaults) bound `L`, as for any row. The path's years go wherever the shocks take them, since a −40% year is a real stock return; only the growth-factor form keeps a year above −100%. A path bound for series whose negative years would be wrong (a cash yield, say) is deferred until one is needed.
- **Shocks are drawn through the tree, every year.** Step `k`'s `εₖ` is the row's score for the calendar year `Y` that step falls in, computed through the row's ADR-008 tree exactly as its level score is, from year-`Y` noise for every node in the tree ([ADR-008](ADR-008-correlated-parameters.md) §5). Keying by calendar year rather than by step number means two process rows in one tree share each year's shock correlation even when their paths start in different years; their shocks are correlated at the same ρ their levels are, year by year. A process row in no tree has independent shocks. In a t-copula tree each year draws its own scale `S`, so a turbulent year moves every process row in the tree at once: that is how a shock year arises from the process rather than from an authored episode. One structure serves levels and shocks alike; a separate tree for the shocks is deferred until a recipe needs one.
- **Member 0** sets every score to 0, levels and shocks alike, so its path is flat at `L`, or with a `current` start decays deterministically from `r_current` to `L`: member 0 has no year-to-year volatility, and so no sequence risk. It stays the deterministic base case §9 describes; the spread comes from the other members.
- **Generated rows are provenance.** As for a ramp, the generated rows are ordinary dated `set_rate` events written into the member's intent, described `ADR-006 process year k for <name>`, so a member's whole path is readable from its own files. `ensemble_draw` records `L` (and its `z`), as for any row.
- **Reporting.** Sensitivity (ADR-007 §2) and the Monte Carlo correlation report (ADR-007 §6) treat `L` as the row's parameter. One-at-a-time sensitivity draws nothing, so its paths are member 0's shape: flat, or a deterministic decay from a `current` start. The year-by-year shocks show up in those reports as spread that no row's parameter explains, which is what they are.
- **Calibration differs from a held row's.** A held row's SD should be the spread of a multi-year average over the span it holds. A process row's level SD covers only uncertainty about the long-run level, since the path supplies the year-to-year spread itself; using the windowed SD for both would count the spread twice. `analysis historical` reports φ (its persistence) and the yearly shock SD for a series; the calibration guide says which to use.

A ramp and a process don't combine on one row: a ramp describes a planned move to a new level, a process the year-to-year spread around one. A ramp row followed by a later process row for the same series expresses both.

### 4b. Resuming what an episode interrupted

An episode (a template like `t_great_inflation`) changes a series for a while and then has to give it back. Copying the long-run values into the episode's own return rows would tie the episode to one long-run recipe, and a mix-in can't name the row it interrupts, since a scenario without an `_ensemble` layer has none. A return row instead names a date, `vary_resume`, normally the episode's start marker, and puts back what governed its `(aux_kind, series)` the day before it.

Pass 2 (§5) finds what governed from the latest authored `set_rate` row for the series dated before `vary_resume`, after pass 1 has drawn the dates:

- **A process row** (§4a) resumes. The row continues that process with its drawn `L`, `φ` and `σ`, starting from the rate in effect on the day before the row's own date, as a `current` start does, and reverting to `L` from there. Its years take the process's own yearly shocks (keyed by calendar year, §4a), so a member with the episode and the same member without it share every shock after the episode, and their paths come back together as `φᵏ` decays the difference. That makes "with or without the episode" a paired comparison. Its generated rows run to the next authored `set_rate` row, like any process's; `ensemble_path_shock` records them under the process's name, and a year the resumed path shares with the process's earlier stretch keeps the earlier entry. Member 0's resumed path decays deterministically, as a `current` start's does.
- **Another resume row**: whatever that row resumed.
- **Anything else** (a series-file entry, a fixed `set_rate` row, a held draw, a ramp): the fixed rate in effect the day before `vary_resume` comes back at once, as the row's `amount`.
- **Nothing**: no rate to put back, an error, as for a `current` start.

A member whose drawn dates put `vary_resume` on or after the row's own date is an error, since the row would put back a rate from its own future; the markers' ranges should keep an episode's end after its start. A resume row draws nothing and adds no `ensemble_draw` row. A scenario that has resume rows and nothing varying still runs through its base case, member 0, so the vary step resolves them; the engine rejects an unresolved resume row as it does a varying one.

### 5. Generation

A new module resolves one recipe intent into `member_count` member intents:

1. Copy the recipe's intent file to `state/intent/<recipe>/member_NNNN.sqlite3`.
2. Query that copy's own `calendar_event` rows and `person_lifespan` rows for `vary_distribution IS NOT NULL`.
3. Pass 1 (dates): resolve each `date_marker` row, after any marker its own dates are written from, drawing it if it varies; then rewrite every date written relative to a marker (`date_refs_json`) from the marker's resolved month; then, for each other `vary_target='date'` row, draw on its own RNG stream (§3), from bounds that have already moved with their marker, and `UPDATE calendar_event SET date = ?, vary_distribution = NULL WHERE name = ?`. The loader wrote relative dates against the markers' base case, so member 0 changes none of them.
4. Pass 2 (amounts/rates): for each `vary_target='amount'` row, in date order (date, then row), draw a value (and, for a ramp, the target — §4; for a process, the level `L` — §4a); either `UPDATE ... SET amount = ?, vary_distribution = NULL` or, for a ramp, that plus `INSERT`ing the additional interpolated rows. A process row instead takes `rate₀` as its own `amount` and `INSERT`s one row per later year, up to the cutoff §4a describes (the scenario's last month, or the next authored `set_rate` for the same `(aux_kind, series)`, whichever is first). Its `ensemble_draw` row records `L`, not `rate₀`, so the parameter the reports read is the level, kept apart from the path built on it. Date order lets a process with a `current` start, or a ramp, start from an earlier row for its series that varies too, once that row's value and its ramp or path rows are written; every row draws on its own stream (§3), so the order moves no draw. Resume rows (§4b) join the same date order: which process each continues is found first, from the authored rows, so its years can be added to that process's yearly shocks before any is drawn; each is then resolved in its place, after the rows it reads.
5. Resolve each varying lifespan's age and final month (§3a).
6. Record what happened (§6) in the same copy.
7. Hand the finished, ordinary intent file to `run_scenario`, unmodified, writing `state/runs/<recipe>/member_NNNN.sqlite3`.

Clearing `vary_distribution` as each row resolves means a finished member intent has no unresolved rows left — by the time `_apply_calendar_event` ever sees these rows, they're indistinguishable from any other authored calendar event.

### 6. Provenance per member, and per batch

Each member's intent carries its own provenance in four tables, added to `SNAPSHOT_TABLES` like any other intent table, so they flow into the run file the same way everything else does, with no special-casing in `open_run_file` (their DDL is in [ADR-002](ADR-002-storage-schema.md)):

- `ensemble_manifest`, one row: the recipe's name, the member's index and the member count, its derived seed (for display; draws key off the master seed, §3), the recipe's `scenario_tree_id` at generation time, and its mode ([ADR-007](ADR-007-sensitivity-analysis.md)).
- `ensemble_draw`, one row per resolved node (a varying row, a lifespan `lifespan:<person>`, or a latent factor): its target, the value drawn in the target column's own unit, its distribution, and how it was drawn. `quantile` is an OAT override ([ADR-007](ADR-007-sensitivity-analysis.md)), `z` its score in a correlation tree ([ADR-008](ADR-008-correlated-parameters.md)), `noise` the node's own standard normal before its tree mixes it in, and `u` the probability the value sits at in its distribution: the quantile for an override, Φ(z) (or the t CDF) for a scored node, 0.5 for a central value, and for an independent draw the uniform its stream gave, read off a fresh copy of the stream so no draw changes. A lifespan's authored base age has no `u`.
- `ensemble_tail_scale`: each t-copula tree's scale `S` on a random member, its own and each process year's.
- `ensemble_path_shock`: each year of a process path (§4a): its noise, score, scale, shock and the resulting rate.

They are present (with real rows) only in a member's own intent and run files; absent (empty) in the recipe's own intent, and in every ordinary, non-ensemble scenario. This is what makes a member self-documenting without diffing databases.

**One database per batch** (#261). Assessing a batch's statistical setup wants every member's draws side by side with the distributions and correlations behind them, so the end of `sim run` (Monte Carlo or sensitivity) gathers the member files into `draws.sqlite3`, beside the member run files, which retention prunes with the batch. Each member's run file is read, or its intent when the run file is missing; a member with neither is listed with no draws. The file is rebuilt whole, never updated (`sim ensemble draws --rebuild` re-gathers it, and gathers one for a batch run before it existed, whose newer columns stay NULL); a failure to write it is a warning, not a failed run. Its tables (`draws_db.DRAWS_DDL`):

- `batch`: the ensemble, batch, mode, master seed (NULL for a sensitivity batch, which draws nothing), member count, versions.
- `member`: every member, `is_base` marking member 0 (§9), its derived seed and run status, and its `component`: the ensemble it was drawn from, the batch's own except in a pool ([ADR-009](ADR-009-pooled-ensembles.md) §7).
- `node`: each varying row, lifespan and factor of each component, keyed by component and name, described from member 0's file (in a pool, a component without member 0 from its lowest-indexed member's): its distribution and parameters as resolved (a `truncated_normal`'s inferred bounds included), process and ramp settings, a life table's sex and set-forward, its base value, its correlation parent and ρ, tree root and ν, and the distribution's own moments.
- `node_pair`: every pair sharing a tree, per component, its implied ρ and expected Kendall τ, and for a Monte Carlo batch the ρ achieved from the drawn members' scores with its 95% interval ([ADR-008](ADR-008-correlated-parameters.md) §6).
- `draw`, `tail_scale`, `path_shock`: every member's rows of the member tables above.
- `draw_check` (Monte Carlo only): per component and node, over its drawn members, the mean, SD and 5th/25th/50th/75th/95th percentiles beside the distribution's own (a factor's standard normal, or t with its tree's ν), and the Kolmogorov-Smirnov distance of the members' `u` from uniform with its asymptotic p-value.

Values are stored in the simulator's units (cents, micros, day ordinals, years), as everywhere else; the `node_display`, `draw_display`, `draw_check_display` and `path_shock_display` views translate to dollars, percent and ISO dates, and `draws_wide`/`draws_wide_display` are member × node matrices of the drawn members, member 0 left out, with each member's component. A database gathered before the component keys is gathered again when read. `sim ensemble draws [ENSEMBLE] [--batch] [--node NAME] [--csv FILE]` prints the database's path and the per-node check and correlated pairs, lists one node's draws, or exports the matrix; `sensitivity.ipynb` has a Draws section on the same file.

**Member intent files are kept, not discarded**, specifically so a failed member's exact input is there to inspect — the recipe scenario plus the concrete draws that produced it, with nothing to reconstruct from a log.

### 7. `sim run` generates the ensemble when a recipe has one

**A scenario is an ensemble when its merged `scenario.meta_json.ensemble_size` is a positive integer**; absent or 0 means it is not. The load checks it: a JSON integer or a string of digits, 0 or more, stored as the integer; a float, a boolean or anything else fails the load. The size inherits key by key and the seed field by field ([ADR-003](ADR-003-registries-and-csv-schemas.md) §4.5), so a scenario's kind and seed come from its parents unless it sets its own. `sim ensemble create <name> <parent> [<mixin> ...]` makes an ensemble: when the parents already make one it inherits that seed and size, writing neither, so member *i* of each draws the same future (§8); `--seed`, `--new-seed` and `--size` override them. Otherwise it records a fresh random seed (or `--seed`) and `--size`, default `registries.DEFAULT_ENSEMBLE_SIZE`. `sim scenario create` writes `ensemble_size` 0, so it never makes an ensemble, even under one: an ensemble can stand in for a scenario as a parent. `sim ensemble list` lists the ensembles, and it and `sim scenario list --verbose` show each scenario's seed and size, `[bracketed]` when inherited. A **pool** ([ADR-009](ADR-009-pooled-ensembles.md)) is an ensemble too, of another kind: its members are other ensembles' members, linked, not drawn, and `sim run` on it builds its batch from theirs.

`sim run <recipe>` loads the scenario as usual. If the loaded intent has any unresolved `vary_distribution` row and is an ensemble, or `--ensemble-size N` is given, it does not produce a single run — it takes `member_count` from `--ensemble-size N` if given, else `ensemble_size`, and the ensemble's own seed from `scenario.seed` (reserved for exactly this since ADR-002 v1; an error if unset). A scenario with varying rows that is not an ensemble runs its **base case** instead: member 0 (§9), resolved to `state/intent/<scenario>/base_case.sqlite3` and run to an ordinary run file, which needs no seed. `sim all` runs every scenario in the data repo the same way `sim load --run` does, so a recipe with a recorded `ensemble_size` runs there too, with no separate ensemble-aware code path. It creates `state/intent/<recipe>/` and `state/runs/<recipe>/`, generates and runs each member (§5), and reports progress. **A member that fails is reported, not retried** — the summary names the failure count and each failed member's intent file path, so the specific input that failed is one open-file away.

If a scenario has no unresolved rows, `sim run` behaves exactly as it does today; no existing scenario's behavior changes.

### 8. Aggregation and reporting

No new engine or storage concept: `member_count` member run files are that many ordinary `RunConnection`s, and combining them is the same net-worth series already used everywhere, one column per member, reduced row by row (month by month) —

```python
wide = members_net_worth_by_month(members)   # one column per member
by_month = summary_with_percentiles(wide)    # mean, median, std, p05, p20…p80, p95
```

— the same shape of aggregation `scenario_compare.ipynb` already does across a handful of named variants, just over many random ones. `members_balance_by_month(members, account, lot=...)` is the same frame for one account's balance, or one lot of it (net worth when `account` is omitted), read with one query per member file.

**The series store.** Rebuilding each member's series from its run file costs tens of milliseconds a member (after-tax net worth most: its drawdown and unpaid tax), which for hundreds of members and decades of months is most of a minute, paid again for each widget and each new account or dollars. So a Monte Carlo batch keeps its members' series in `series.sqlite3`, beside the member files (`sim/series_db.py`), and the notebook and `sim ensemble summary|compare` read that instead: one indexed query per subject for every member. Each process `sim run` runs a member in reads that member's rows from its run file as it finishes, so the work runs in parallel with the members; the batch's process writes the file once they're all done. It holds, per succeeded member, its index and seed (for pairing), months, CPI index, the engine's CPI-constant net worth, deaths, and what guard rails read besides the series (the household's last death, the `date_marker` dates, each account's kind, subkind and tags), each month's transfers summed by from account, to account and, for a rule's expense, the rule's tags (`RunConnection.monthly_flows`), the batch's target sets and the strategies steering to them ([ADR-010](ADR-010-responsive-strategies.md) §7), and per subject (net worth, after-tax net worth, every account, every asset or liability lot, and the dollars in each asset class for every asset lot and for each account tag's) the nominal values by month: integer cents stored as month-to-month differences, after-tax net worth as float dollars, each zlib-compressed. Other CPI-constant figures are converted at read time, by each member's own index and with the functions `RunConnection` uses, so the store and the member files agree to the bit. A store is trusted only when it matches the member files it was built from (each one's size and modification time), the format, and a hash of the code that derives the series (`connection.py`, `series_db.py`, `drift.py`, `asset_classes.py`). Otherwise, and for a batch run before stores existed, the first reader builds it, the notebook with a progress bar counting the members, and later reads are quick. The file is rebuilt whole, never updated; a failure to write it at the end of a run is a warning, not a failed run. The notebook's widgets share the stores they open, by batch, so a recipe one widget has read is ready for the others. A new `notebooks/ensemble.ipynb` plots the standard Monte Carlo fan (quintile bands over time, shaded darker toward the middle and out to a 5th–95th-percentile envelope) for net worth, any one account, or one lot of an account with several, over a year-end table of mean, median, SD, the `p05`, `p20`…`p80`, `p95` percentiles, and the tail means below, all from `ensemble.summary_with_percentiles()` and `ensemble.risk_summary()`. Min and max are deliberately not reported: with a large ensemble they sit far past where most members land and are easily read as typical outcomes when each is one member's luck. `sim ensemble summary <recipe> [--account NAME [--lot LOT]]` is the terminal equivalent from day one, printing the same table (a header row over aligned columns) plus the failure count from §7, so this doesn't join the CLI-gap backlog in `TODO.md`.

**Tail means and the reserve.** Risk is reported as the mean of the worst 5% and the worst 20% of members (`cvar05`, `cvar20`: CVaR, or expected shortfall; `ensemble.TAIL_LEVELS`), each rounded up to whole members, at least one. A tail's mean is steadier than the single breakpoint at its edge, which with tens of members is one or two members' luck, and it says how bad the bad futures are rather than where they start. The two levels are fixed: a standard pair leaves nothing to tune until a comparison looks better without new information. A recipe may set a **reserve** in `scenario.meta_json` (`{"reserve": 250000}`, CPI-constant dollars, whole dollars or a `"250000.00"` string; inherited key by key like `ensemble_size`, and checked at load). It is a floor for net worth; when set, the table adds `below_reserve`, the share of members below it at that date, and `ever_below_reserve`, the share that have been below it at any month so far. Both are always measured in CPI-constant dollars, whatever dollars the table shows. The notebook and `--reserve` can override it for one report, and an override applies to whatever is shown, an account included.

**Comparing ensembles.** Comparing two recipes' member 0s compares their centers, not their risk; `scenario_compare.ipynb` still does that, which stays useful for checking a recipe's configuration. The ensemble notebook's head-to-head comparison (`ensemble_compare_widget`) and `sim ensemble compare <baseline> <variant>` compare two whole ensembles, net worth or one account, the variant against the baseline, the notebook's as charts only; the notebook's table (`ensemble_table_widget`) sets a baseline against any number of recipes, each row one (year, recipe), with the same deltas and each recipe's tail means. In the notebook a comparison offers only recipes that pair with the baseline (below): a comparison that can't pair members has no per-future differences, the part that says most. Each widget picks its own recipes; only the scale, dollars, account, reserve and years are shared.

- **Percentile deltas** (`quantile_deltas`): each `pNN` minus the same `pNN` of the baseline, month by month. Valid for any two ensembles, but the members at a breakpoint are different futures on each side.
- **Paired deltas** (`member_pairs`, `paired_deltas`): draws are keyed by (seed, member, row name) (§3) and a child inherits its parent's seed (§7), so member *i* of each recipe drew the same value for every row they share. Pairing members by index when their recorded seeds match makes `variant − baseline` a per-future difference: its own fan, and `P(ahead)`, the share of futures where the variant comes out ahead. A row only one recipe has draws on its own stream, so it is part of the difference being measured, not a break in the pairing; for the same reason, two member counts pair over the indexes both have. Recipes with different seeds don't pair: `sim ensemble compare` says so and shows the rest, and the notebook doesn't offer them.
- **Tail deltas**: `Δcvar05`, `Δcvar20`, with a reserve `Δbelow_reserve` and `Δever_below_reserve`, and each recipe's own tail means and reserve shares.

The account choices are every account any compared recipe has. An account only one side has can't be subtracted: that pair gets a note and the side that has it its own fan (in the notebook's table, its own tail means).

No confidence bands are drawn on any of these: they don't read well over a fan, and the remedy for a noisy difference is more members (see `docs/guides/ensembles.md` for sizing).

**Guard rails.** A recipe's guard rails (ADR-003 §4.11) are a lens on its batch, as on one run: read from the data repo when a report asks, never part of the batch, so editing one reruns nothing. The store's transfer totals are enough to rebuild any rail's spending or withdrawals, whatever its `select` or `portfolio` tags, and each member is evaluated exactly as its own run file would be (`guard_rails.evaluate_ensemble`). The rails are read once for the batch and not checked against one member's run (`sim check` checks them against the scenario): a tag a member lacks matches nothing there, and a rail bounded by a `date_marker` the member lacks covers none of its years. Per rail, form (annual and cumulative margin) and year, across the members the rail covers (it stops at each member's household's last death):

- `past`: the share of members past the rail that year;
- `ever_past`: the share past it in some year so far, as `ever_below_reserve` is for the reserve, of every member it has covered so far (a member whose household has ended still counts, past or not, so the share can't exceed one);
- `rms_over`: the root mean square of how far past the members are, those inside counting as zero, in the report's dollars.

These are the lower partial moments of downside-risk finance: the share past is the zeroth, and the RMS overshoot is the square root of the second (the target semideviation behind the Sortino ratio). Squaring weighs one large miss more than several small ones, and counting members inside as zero mixes how often with how far, which is why it is always shown beside the share. Over the whole run, per rail and form: the share of member-years past, the share of members ever past, the share past in each member's last covered year (for the cumulative form, the members who end the plan overdrawn), and the RMS over every member-year. `sim ensemble guard-rails <recipe> [--rail NAME] [--graph]` prints them and the notebook's guard rails widget draws them, shares over RMS, annual beside cumulative. `sim ensemble compare` adds each rail both recipes have, matched by name: the variant's change in each share and RMS, year by year. The notebook's guard rails table (`ensemble_guard_rails_table_widget`) does the same for a baseline and any number of recipes that pair with it, each row one (year, recipe), then each recipe's whole-run summary with its change against the baseline.

**Charts in the terminal.** The fan chart and the comparison's panels are plain matplotlib figures in `sim/ensemble_plots.py`, free of the widget layer, so the notebook widgets and `sim ensemble summary|compare --graph` draw the same charts. `--graph` draws them after the tables, in the terminal through the kitty or iTerm2 image protocol as `sim chain show --graph` does, or into a temporary PNG when the terminal can't show images; `--graph-file X.png|.svg` writes the chart instead. `--account`, `--lot`, `--reserve` and `--dollars` shape the chart as they shape the tables. The summary is in nominal dollars, so its chart draws no reserve line (the reserve is CPI-constant, and the notebook draws it only on a CPI-constant chart).

### 9. Member 0: a deterministic base case

Every ensemble's member 0 resolves each `vary_distribution` row to its distribution's **central value**, its median (`uniform`'s midpoint; `truncated_normal`'s authored `vary_median`, exact even with asymmetric bounds; `triangular`'s median — #31; a lifespan's authored age instead, §3a) instead of drawing from its RNG stream — members 1 through `member_count - 1` draw exactly as before, unaffected. This gives every ensemble one deterministic, always-in-bounds "base case" member, and lets anything that only knows how to open one run file per scenario (a notebook's scenario picker, any other single-scenario tool) treat an ensemble recipe's member 0 as that scenario's run the same way it would any ordinary scenario's — `resolve_scenario_name` falls back to member 0 of the latest batch when there's no flat run file to find.

This is a deliberate, small distortion of the sampled distribution: member 0 isn't actually drawn from it, so a statistic computed across *all* `member_count` members (mean, SD, a fan chart's percentile bands) is very slightly biased toward the center relative to `member_count` genuinely independent draws — most noticeable at a small `member_count`, negligible at the sizes this ADR expects (tens of members; see `docs/guides/ensembles.md` for sizing guidance). The alternative considered was keeping member 0 out of the statistics (effectively `member_count + 1` members: one deterministic, `member_count` random) or dropping the guaranteed base case entirely (every member drawn, as originally designed). Both were rejected: a single always-present, always-inspectable member is worth more than the statistical purity of excluding it, and "member 0 is special, full stop" is a simpler invariant to hold onto than a count that means something different depending on whether you're drawing a member or aggregating across them.

- [ADR-004](ADR-004-reproducibility-and-activation.md): a member's provenance is the recipe's `scenario_tree_id` (unchanged meaning, copied via the intent copy) plus `ensemble_manifest` for which member and what it drew — not a new parallel determinism mechanism.

## Consequences

- Positive: `run_scenario`/`open_run_file` need no ensemble-awareness at all; a member is an ordinary intent-then-run pair readable by every existing tool; variation authoring reuses calendar reporting instead of inventing a parallel, invisible mechanism; a failed member's exact input is a file on disk, not something to reconstruct.
- Negative: `calendar.csv` needs the schema addition before any of this works; an ensemble's disk footprint is `member_count` full intent files *and* `member_count` full run files (neither a diff); wall-clock time for `sim run` on a recipe scales linearly with `member_count`; member 0 being deterministic rather than drawn (§9) is a small, deliberate bias in any statistic computed across every member.
- Not attempted: nested ensembles (a recipe whose parent is itself a recipe); varying a target that isn't expressible via `set_rate`/`set_amount`/`one_off_transfer` (an opening balance, say) — add a case when a real need appears, per this project's own registries-grow-one-line-at-a-time convention.

## Open questions deferred

- Shaped (skewed or heavy-tailed) shocks for a process (§4a), a separate tree for its shocks, and bounds on its path — each when a recipe needs it; the t-copula's per-year scale already gives fat-tailed, simultaneous shock years.
- Additional distribution families (lognormal, ...) — useful flexibility, not a present requirement. (Skew/kurtosis controls and `triangular` were added by #31.)
- Correlated draws across variations — today every variation is independent; no rationale identified yet for coupling two.
- A variation whose value should be computed from *another* variation's resolved draw (beyond the date-before-amount ordering in §3) — not needed yet; the two-pass rule covers every case raised so far.
